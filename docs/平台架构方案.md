## 1. 为什么要拆产品

`raw_datasets` 九大包横跨国内工商拓客、外贸出海、资本人物与政研金融，三类数据在最根本的维度上不同：

| 维度 | 国内工商线索 | 外贸 / 海外买家 | 资本人物 / 银行 / 官员 |
|------|--------------|-----------------|------------------------|
| 主键 | 统一社会信用代码 | 邮箱 / 提单号 / 英文商号 | 股票代码、PersonID、行政区划 |
| 用户 | 销售、招商、渠道 | 外贸业务、跨境获客 | 研究、风控、投研 |
| 作业单元 | 一家存续企业 + 手机号 | 一票货 / 一个海外买家 | 一个人 / 一家上市主体 |
| 合规敏感点 | 国内联系方式 | 跨境数据、个人通讯录 | 高管薪酬、公务人员 |
| 检索心智 | 省市区 · 产业链 · 有手机 | HS · 目的国 · 采购商 | 任职 · 学历 · 任期 |

硬揉进一张主表会导致大量 NULL 列、筛选语义分裂、ETL 互相踩断点、开源与商用边界说不清。

**核心原则：产品分家 · 数据湖共用 · 实体层打通 · 代码单仓 · 运行时独立。**

## 4. 实体层：`bzid`

### 4.1 为什么必须有

海外买家没有信用代码，董监高的键是 `Stkcd + PersonID`，未来还有招投标、专利、司法。若「谁要关联谁就建一张桥」，六个源就是 15 条桥，每条各自维护匹配逻辑，规则必然漂移。

**统一为：任何源只回答一个问题——「我这条记录指向哪个 `bzid`」。**

### 4.2 表设计

```sql
-- 主体注册表：一个现实世界组织一行
CREATE TABLE entity_master (
    bzid            VARCHAR(24)  NOT NULL COMMENT '内部主体 ID',
    primary_type    VARCHAR(16)  COMMENT 'cn_company / oversea_buyer / bank / listed',
    canonical_name  VARCHAR(300) COMMENT '规范名（中文优先）',
    country         VARCHAR(8)   DEFAULT "CN",
    created_at      DATETIME,
    updated_at      DATETIME
) UNIQUE KEY(bzid)
DISTRIBUTED BY HASH(bzid) BUCKETS 32;

-- 别名 / 外部标识映射：多对一
CREATE TABLE entity_alias (
    id_type     VARCHAR(24)  NOT NULL COMMENT 'credit_code/stock_code/tax_id/email_domain/name_fp_cn/name_fp_en',
    id_value    VARCHAR(200) NOT NULL,
    bzid        VARCHAR(24)  NOT NULL,
    confidence  DECIMAL(4,3) COMMENT '1.000 = 强标识；名称指纹通常 < 0.95',
    source      VARCHAR(32)  COMMENT '哪个包 / 脚本写入',
    method      VARCHAR(24)  COMMENT 'exact / normalized / fuzzy / manual',
    loaded_at   DATETIME
) UNIQUE KEY(id_type, id_value)
DISTRIBUTED BY HASH(id_value) BUCKETS 32;
```

### 4.3 标识强度与冲突

| 标识 | 强度 | 说明 |
|------|------|------|
| `credit_code` | 强 (1.0) | 国内主体首选，直接决定 bzid |
| `stock_code` / `tax_id` / `org_code` | 强 | 可传递合并 |
| `email_domain` | 中 | 海外买家主用；gmail 类公共域**不可**作键 |
| `name_fp_cn` / `name_fp_en` | 弱 (≤0.9) | 仅作候选，需二次确认 |

同一强标识指向两个 bzid → 触发合并任务，保留较早 bzid，另一个记入 `entity_merge_log`，不物理删除。弱标识冲突一律进人工队列，**不自动合并**。

### 4.4 对现有实现的影响

`companies` **保持 `credit_code` 作主键不变**，新增可空列 `bzid` 异步回填——不破坏现有查询与 ETL。

## 5. 多租户与计量

### 5.1 现状差距

当前是单机内部工具：`user_id` 是普通查询参数（可冒用）、`allow_origins=["*"]`、Doris root 空密码、`replication_num=1`。作为 SaaS 需全部整改。

### 5.2 库的物理分离

| 类别 | 库 | 内容 | 特点 |
|------|-----|------|------|
| 公共只读 | `qcc` / `trade` / `research` | 工商、标签、提单 | 所有租户共享，ETL 唯一写入方 |
| 租户私有 | `tenant_core` | 跟进状态、片区、收藏、导出记录、备注 | 带 `tenant_id`，可整租户删除 |
| 平台 | `platform` | 账号、套餐、配额、审计、计量流水 | 与业务数据隔离 |

> 现有 `contact_status` / `sales_territory` 在 `qcc` 里，需迁至 `tenant_core`，否则退租与合规删除会牵动公共库。

### 5.3 身份 · 脱敏 · 配额 · 审计

- 租户身份来自 **JWT / API Key**，不再从查询参数读 `user_id`
- 三级角色：`owner` / `member` / `agent`（Agent 默认只读 + 更严配额）
- **字段级脱敏**：列表默认 `138****5678`；完整号码走 `reveal_contact`，该调用即计量事件
- 计量事件写 `platform.usage_events`：`reveal_contact`(1) · `export_rows`(N) · `deep_scan`(按分片)
- 配额闸门放在**网关**，不在业务代码里重复实现；超限返回结构化 `QUOTA_EXCEEDED`
- 所有联系方式读取写审计流水（谁、何时、哪家、何用途、UI 还是 Agent）

## 6. 查询分层与性能

### 6.1 三条路径与 SLA

| 路径 | 典型查询 | 目标 | 实现 |
|------|----------|------|------|
| **点查** | 信用代码、手机反查、企业详情 | **< 50ms** | 主键直取，禁止进入扫描计划 |
| **筛选统计** | 省市区 + 产业链 + 有手机 + 计数 | **< 1s** | 预聚合物化 + 冗余标志位 |
| **全文语义** | 公司名模糊、经营范围检索 | **< 2s** | Doris 倒排；不够再外置检索引擎 |

每个对外接口都要**明确归属哪一层**，不允许「看起来是点查、实际全表扫」。

### 6.2 四项必做改造

**① facets 物化** — `/api/facets` 目前每次实时 `GROUP BY` 全表。改为定时刷新的 `facet_cache(dim, key, cnt, updated_at)`，首屏从秒级降到毫秒级。

**② 游标分页替代 OFFSET** — `LIMIT n OFFSET m` 在千万级越翻越慢。改用 `search_after`，以 `(sort_key, credit_code)` 为游标返回 `next_cursor`。Agent 会连续翻页，这条对它尤其重要。

**③ 资源组硬隔离** — 同机同 BE 单副本做不到「导入不影响查询」。用 Doris **Workload Group** 给在线查询与批量导入划分 CPU/内存配额，导入永远让路。

**④ 副本与冷热** — `replication_num=1` 对 SaaS 不可接受，公共库上线前升到 **≥2**。历史提单、09 海外通讯录等低频数据下沉冷存储。

### 6.3 容量提醒

01 包 49GB xlsx 入仓后约 300GB+ 量级，09 另有 18GB 原始。**按「三产品全量 × 副本数」倒推存储**，这是决定「同机多库 → 分实例」时点的主要指标。

## 7. Agent 接入与语义层

### 7.1 三条原则

1. **不让 Agent 写 SQL** —— 生成式 SQL 直连 Doris 同时带来注入风险与全表扫描，一次失误就能拖垮在线查询。
2. **Agent 面对一套工具，不面对三个服务** —— 它不该判断问题归之眼还是出海，由网关按实体路由。
3. **契约稳定优先于功能丰富** —— Agent 对字段改名、排序不稳定、错误不结构化极其敏感。

### 7.2 工具集（MCP / OpenAPI 双暴露）

| 工具 | 用途 | 层 |
|------|------|-----|
| `describe_schema` | 返回可用字段、枚举值、可筛维度 | 元数据 |
| `search_companies` | 结构化条件检索，返回游标 | 筛选 |
| `get_company` | 按 `credit_code` / `bzid` 取详情 | 点查 |
| `list_contacts` | 联系方式（默认脱敏） | 点查 |
| `reveal_contact` | 明文号码，**计量 + 审计** | 计量 |
| `get_chain_tags` | 产业链 / 资质标签 | 点查 |
| `search_shipments` | 出海提单（出海上线后） | 筛选 |
| `resolve_entity` | 名称 / 邮箱 → `bzid` | 实体层 |

`describe_schema` 常被忽略却最关键：让 Agent 自己发现「产业链有哪些取值」，而不是靠猜或硬编码。

### 7.3 契约要求

- **确定性排序**：列表一律以 `(sort_key, credit_code)` 全序，同参数必得同结果
- **游标分页**：返回 `next_cursor`，不暴露 offset
- **结构化错误**：`QUOTA_EXCEEDED` / `INVALID_PARAM` / `NOT_FOUND` / `TOO_BROAD`
- **`TOO_BROAD` 保护**：预计扫描量超阈值直接拒绝并**建议收窄维度**，而不是硬跑几十秒
- **只读凭据**：Agent token 无写权限、配额独立计，避免高频重试打穿人类用户额度

### 7.4 与 UI 的关系

UI 和 Agent **走同一套网关 API**，UI 不再直连领域服务。脱敏、配额、审计只实现一次，且不会出现两套割裂能力。

## 8. 代码组织：单仓多包，运行时独立

### 8.1 为什么不用多仓

**独立部署 ≠ 独立仓库。** 部署独立性来自独立进程、独立数据库、独立 CI 流水线，与 git 仓怎么切无关。多仓真正的代价是**清洗规则静默漂移**——而这在当前单仓里已经发生：

- 空值哨兵两份：`etl/load_jzh.py` 有 19 个，`scripts/quality_scan.py` 只有 14 个（缺 `nan`、`null值`、`*`、`**`、`???`）。后果是质量扫描把 `nan` 当有效值，填充率报高——而 `sql/01_schema.sql` 的字段长度正是依据这份扫描确定的。
- 信用代码正则三份两种：`load_jzh.py` 与 `build_leads.py` 是 `^[0-9A-Z]{18}$`，`app/main.py` 是 `^[0-9A-Za-z]{15,18}$`。

一个仓、一个人都会漂；三个仓、三个人、三个时间点只会更快。

**上了实体层后果会更严重**：`name_fp_cn` 指纹若两边规范化规则不同，同一家公司算出两个 `bzid`——**不报错、不崩溃、日志干净，只是永远关联不上**。手机号同理：两边归一化不同会在 `contacts` 里同时留下 `010-12345678` 和 `01012345678`，`UNIQUE KEY` 管不住。

### 8.2 目标结构

```text
baize/                          # 私有主仓
  packages/
    baize_core/                 # 唯一的规则副本
      cleaning.py               # 空值哨兵、正则、字节截断、多值拆分
      capital.py                # 资本解析 + 汇率 + 脏数据纠偏
      region.py                 # 省份 / 状态归一
      dates.py                  # 日期解析
      xlsx.py                   # 流式读
      doris.py                  # Stream Load 客户端
      entity.py                 # 名称规范化 + 指纹 + bzid
  services/
    eye/                        # 白泽之眼：API + UI + ETL
    trade/                      # 白泽出海
    research/                   # 白泽研析
    gateway/                    # 网关 + MCP 语义层
  deploy/                       # 每服务一个 Dockerfile / compose
  docs/
```

每个 `services/*` 有独立 `Dockerfile`、独立 `DORIS_DB`、独立端口、CI 按路径过滤触发。出海挂了不影响之眼，出海发版不需要之眼跟着发。

### 8.3 防漂移三条约束

1. **`baize_core` 是唯一副本**：清洗哨兵、正则、资本解析、区划归一、字节截断、Doris 客户端、名称规范化与指纹，只能存在于 core，其他服务禁止本地重定义。
2. **黄金用例契约测试**：core 内置固定输入输出（`"1000万美元" → (7200.00, "美元")`、`"nan" → None`、`"010-1234 5678" → landline "010-12345678"`），所有服务 CI 跑同一份。谁重写了逻辑或升级后行为变了，测试立刻红——这是唯一能自动拦住漂移的机制。
3. **宽松匹配不进 core**：`app/main.py` 那份 `^[0-9A-Za-z]{15,18}$` 是「用户搜索框输了什么」的识别，与「这个码合不合法能否入库」是两件事。core 放严格版，宽松识别留在网关查询解析层。

### 8.4 两步迁移（不要现在大搬家）

当前 01 全量补全未跑、断点目录在用、开源仓链接有效、`sys.path.insert` 遍布 ETL。此时动目录收益为零、风险不小。

**第一步（现在，低风险）**：在现仓建 `baize_core/` 包，把规则从 `etl/load_jzh.py` 抽出。**现在就用未来的名字**——第二步只需 `git mv baize_core packages/`，所有 `from baize_core.cleaning import ...` 一个字不改。旧模块保留 re-export，现有脚本照常运行。同时修掉 §8.1 的两处漂移，补上黄金用例测试。

> 附带解决一个隐性耦合：`etl/load_jzh.py` 已事实上成为公共规则库——`load_chain_xlsx`、`enrich_national_2023`、`load_monthly`、`repair_capital` 都从它 import 清洗函数，导致「江浙沪皖导入脚本」成了全仓依赖根。

**第二步（出海立项时）**：`baize_core` 稳定后，目录提升为 `packages/` + `services/`，纯物理移动。

### 8.5 开源仓的处理

`ai-guoke/baize-eye-leads` 公开，但出海与研析不应公开。两个选择：

- 主仓私有，用 `git subtree split` 单向推送 `services/eye + packages/baize_core` 到公开仓——代码同步，有维护成本
- 公开仓退化为产品门面（README + 截图 + 文档），不再同步代码——省事，但不算真开源

若开源诉求偏展示，选后者更省心。**待定，见 §11。**
