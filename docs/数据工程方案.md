# 第二部分 · 清洗规则（代码契约）

> 本部分是全平台唯一规则来源，将来抽入 `baize_core`（见架构方案 §8）。

## 4. 空值哨兵

下列值（去首尾空白、大小写不敏感）一律视为 **NULL**：

```
空串、-、--、—、–、无、null、none、n/a、na、/、\、
暂无、未知、nan、null值、*、**、???
```

实现：`load_jzh.EMPTY` / `is_empty()` / `clean()`。

> ⚠️ 已知漂移：`scripts/quality_scan.py` 的副本缺 `nan`、`null值`、`*`、`**`、`???` 五个，会把它们当有效值导致填充率报高。抽 `baize_core` 时一并修正。

## 5. 主键与去重

| 情况 | 规则 |
|------|------|
| 合法信用代码 | `^[0-9A-Z]{18}$`（入库前大写、去空格） |
| 缺失或非法 | 代理键 `N` + `MD5(公司名)[:17].upper()`，共 18 位 |
| 同码多行 | Doris `UNIQUE KEY(credit_code)` + `sequence_col = fill_score`，**保留字段更全的一条** |

- `fill_score` = 该行非空源字段数；回填 street / 坐标时 `+1` 以覆盖旧行
- 公司名为空 → **丢弃**（计入 `bad_rows`）
- 字符串按 Doris **字节长度**截断（`tb()`），不是字符数

> ⚠️ 已知漂移：`app/main.py` 的 `CREDIT_RE` 是 `^[0-9A-Za-z]{15,18}$`。那是「用户搜索框输了什么」的宽松识别，与入库合法性校验是两件事，**不应进 `baize_core`**，留在查询解析层。

## 6. 省份 / 城市 / 区县

- **省份归一** `PROVINCE_MAP`：短名 → 标准全称（`浙江`→`浙江省`、`广西`→`广西壮族自治区`）
- **兜底省份** `GROUP_PROVINCE`：源目录名决定兜底省，用于省份字段为空
- **地区串解析**（月度增量）：`江苏-苏州市-吴中区` 按 `-` / `—` / `/` 切分；首段走 `PROVINCE_MAP`；直辖市二/三段落到「市 / 区」
- 城市、区县名保留源表原文（经空值清洗与截断），不做拼音或简称强制展开

## 7. 登记状态归一（`STATUS_MAP`）

| 原文示例 | 归一 |
|----------|------|
| 存续、正常、在业、开业、在营、在册、存续/在业、迁入 | **存续** |
| 迁出 | **迁出** |
| 注销、已注销 | **注销** |
| 吊销、吊销未注销、吊销已注销、撤销 | **吊销** |
| 清算 | **清算** |
| 停业 | **停业** |

未命中映射的原文按 `load_jzh` 当前实现处理。业务默认筛「存续」。

## 8. 注册资本 / 实缴资本

解析模式：`数字 + 可选(万|亿) + 可选币种`。

1. 去千分位逗号
2. 单位：`万`→×1，`亿`→×10000，**无单位按「元」→×0.0001 万元**
3. 币种按固定汇率折人民币万元（`FX`：美元 7.2、港元 0.92、欧元 8.0…）
4. **脏数据纠偏**：单位为「万」且 `数字×汇率 ≥ 1e8`，或 `≥ 1e7` 且非央企白名单 → 按「元」重算；**只允许改小，禁止放大**
5. 结果仍 `> 5e8` 万元 → 资本置空（保留已解析币种）
6. 保留 `capital_raw` 原文备查

回修脚本：`etl/repair_capital.py`。

## 9. 日期

- 匹配 `YYYY-MM-DD` / `年月日` / `.` 分隔；年份限 1800–2100
- Excel 序列号（约 20000–60000）按 1899-12-30 基准换算
- 解析失败 → NULL
- 衍生：`established_year`、`company_age`（相对导入当日）

## 10. 联系方式 → `contacts`

**拆分**：手机 / 更多电话 / 邮箱字段按 `,，;；、空白|` 拆多值（`split_multi`）。

| 类型 | 规则 | `contact_type` |
|------|------|----------------|
| 手机 | 抽数字后匹配 `^1[3-9]\d{9}$` | `mobile` |
| 座机 | 数字长 7–13；像手机的改走手机；保留原形（可含区号 `-`） | `landline` |
| 邮箱 | 标准邮箱正则；转小写 | `email` |

- 同企业同类型同值去重（`UNIQUE KEY(credit_code, contact_type, contact_value)`）
- `source` 标记批次；`collected_at` 记批次截止日
- 主表冗余：`has_mobile` / `has_landline` / `has_email` / `has_contact` / `mobile_count` / `email_count`
- **通信地址**：原文 `地址A\t;\t地址B` → 拆分去重后用 ` | ` 拼接

## 11. 街道解析

### 11.1 标准库

`admin_divisions`（高德 district 区划接口一次拉取，非按企业计费）：江浙沪皖四级，街道级带 `center_lng` / `center_lat`，约 4401 条。

### 11.2 匹配优先级（`street_utils.extract_street`）

1. **默认只走标准库最长匹配**（按市+区索引，街道名按长度降序）
2. 去掉地址前的省市区、高新区/开发区等前缀再匹配
3. 别名：地址写「××镇」可落到库中「××街道」
4. **正则降级默认关闭**（`allow_regex_fallback=False`），避免「淳化街道淳化镇」类脏名
5. 全量回填 `backfill_street.py`：**仅标准库命中才写入**

### 11.3 脏名治理

禁止用宽松正则把半截地址当街道入库；下拉与地图聚合读标准库或已清洗的 `companies.street`；UI 侧的长度与模式过滤只是兜底，根治靠标准匹配回填。

## 12. 地理坐标

### 12.1 定稿：街道中心点回填（免费，地图主路径）

**原则**：地图拓客只需街道/区县级精度，**禁止**对全库逐条调高德地址→坐标 API（按次计费）。坐标取自区划库已有的 `center_*`，企业侧只做匹配赋值。脚本 `etl/geocode_by_street.py` 不读 Key、不打 geocode 接口。

**候选企业**：`lng IS NULL` + `street` 非空 + `status='存续'`，可选 `--only-mobile`。排序 `has_mobile DESC, capital_wan DESC`。

**命中顺序**：
1. 街道中心（主）——`(省,市,区,街)` → `level='street'` 的 `center_*`；省字段偶发不一致时按市+区+街道名命中，仍标 `geo_precision=street`
2. 区县中心（回退）——默认 `--fallback district`；`--fallback none` 可关
3. 仍无点 → 跳过，不写库

**写入**：`lng` / `lat`（抖动后 `round(...,6)`）· `geo_precision` · `geocoded_at` · `fill_score+1`，走 partial columns Stream Load。

**同街道抖动**：按 `credit_code` 做 MD5 确定性偏移，默认半径约 ±120 米（`--jitter 0` 可关）。同一信用代码每次落点相同，非随机。

**坐标系**：GCJ-02（高德）。**不是门牌精度**，只够气泡聚合与列表。门牌级仅小样本可选 `etl/geocode_amap.py`（计费）。

**依赖**：先 `backfill_street` 保证街道为标准名，再跑本脚本；区划中心更新后需重跑才刷新。

### 12.2 地图与列表口径

| 场景 | 口径 |
|------|------|
| 地图气泡计数 | 需有坐标；市/区/街层按**行政区全量已定位**计，不与视野裁切 |
| 点气泡侧栏 | `require_geo=0`，**含未定位**企业 |
| 顶栏「可视区域 N 家」 | 当前视野框内已定位点数 |
| 街道及更细缩放 | 不再下钻网格/单企点；点右侧列表才出定位针 |

# 第三部分 · 入库与流水线

## 15. 目标表结构

```text
companies       主体宽表（工商 + 触达标志 + 坐标 + 简介）
contacts        一号一行，可持续补全
tags            产业链 / 荣誉 / 融资（一企一行，ARRAY 多值）
qualifications  资质证书明细（规划，高新等，一证一行）
admin_divisions 标准四级区划 + 街道中心点
```

三张主表按 `credit_code` colocate 分桶，JOIN 本地化。`companies` 用 `UNIQUE KEY` + `sequence_col=fill_score` 保留更全行。

## 16. 多源补全原则（核心）

**不是整库替换**，按 `credit_code` 对齐：

```
主库已有非空字段  →  保留（不用较差源覆盖）
主库为空、源非空  →  写入
主库无此主体      →  新增
电话邮箱          →  追加 contacts，永不删旧号
产业链 / 荣誉     →  合并写 tags，不整表覆盖
```

实现：按批 `SELECT` 已有行 → 只拼「补空」列 → Stream Load **`partial_columns=true`**，`fill_score` = 旧分 + 新填字段数。

**产业链标签**不建第二套主表，按信用代码聚合多主题多节点；旧数据若把多主题塞进单个 ARRAY 元素（`A | B | C`），筛选侧兼容 `array_contains` + `array_join LIKE`。

断点键 = 文件名 + 字节数；`--reset` 清空重跑，已成功文件 SKIP。

### 17.3 试点先行

# 第四部分 · 展示设计

> 这是数据类型变多后最容易失控的一环：**入库越全，页面越容易变成一堵空值墙**。  
> 核心思路：**用真实填充率决定字段放哪一层，用区块化决定详情页怎么长**。

## 18. 三条总原则

**① 覆盖率决定层级，不是「重要性」决定层级。**  
一个字段感觉再重要，若全库只有 2% 有值，把它固定摆在首屏就意味着 98% 的用户看到空白。

**② 有才显示，空则整块隐藏。**  
单字段为空显示 `—` 可以接受；**整个区块全空时必须折叠或隐藏**，否则详情页会出现连续几屏的 `—`。

**③ 来源与时间要能查。**  
多源合并后用户一定会问「这个手机号哪来的、什么时候采的」。`contacts` 已有 `source` / `collected_at`，但 UI 目前只显示 source 字符串，需要补新鲜度呈现。

## 19. 字段分层（依据实测填充率）

以 7470 万主体为分母：

| 层级 | 判据 | 字段 | 位置 |
|------|------|------|------|
| **L1 核心** | 覆盖 > 90%，决策必需 | 状态 99%、企业类型 99%、税号 99%、核准 97%、营业期限 96%、组织机构代码 95%、注册号 91%、法人、资本、成立、省市区、行业、地址 | 列表列 + 详情首屏 |
| **L2 常规** | 覆盖 40–90% | 英文名 67%、年报地址 65%、通信地址 40% | 详情次级区块，默认展开 |
| **L3 稀疏** | 覆盖 5–40% | 实缴资本 17%、曾用名 9% | 详情区块内，有值才渲染 |
| **L4 稀有但高价值** | 覆盖 < 5% | **网址 2.3%**、**企业简介 1.0%**、产业链标签 1.8%、**荣誉资质 0.18%** | **有才显示的独立区块**，且是差异化亮点 |

L4 这四项是当前实现的主要问题：`intro`、`registrar` 等区块目前无条件渲染，99% 的企业会看到空块。**改为条件渲染。**

反过来，L4 恰恰是产品的差异化——有产业链标签或荣誉的企业应该在**列表页就有视觉标识**（一个小徽章），让用户一眼看出「这家有料」。

## 20. 详情页：从固定布局改为区块注册表

随着数据类型增加（资质证书、外贸、董监高…），硬编码区块会越来越难维护。改为声明式：

```text
区块 = { key, 标题, 数据来源, 是否有数据判定, 加载方式, 排序权重 }
```

| 区块 | 数据源 | 加载 | 空时 |
|------|--------|------|------|
| 基本信息 | `companies` L1 | 同步 | 恒显示 |
| 产业链与荣誉 | `tags` | 同步 | **隐藏** |
| 联系方式 | `contacts` | 同步 | 显示「暂无」+ 录入入口 |
| 资质证书 | `qualifications` | 懒加载 | **隐藏** |
| 标识与资质 | `companies` L1/L2 | 同步 | 恒显示 |
| 地址与网络 | `companies` L2 | 同步 | 恒显示（地址覆盖率高） |
| 企业简介 | `companies.intro` | 同步 | **隐藏** |
| 经营范围 | `companies.scope` | 同步 | 恒显示 |
| 外贸记录 | 出海 API | **懒加载 + 失败静默隐藏** | 隐藏 |
| 关联人物 | 研析 API | 懒加载 | 隐藏 |

关键点：**跨产品区块一律懒加载且失败不影响主页面**。出海服务没上线或挂了，之眼详情照常打开。

## 21. 多值与时序数据的展示

不同数据类型需要不同的呈现形态，不能一律拍成键值对：

| 数据形态 | 展示方式 | 例子 |
|----------|----------|------|
| 枚举 / 短文本 | 键值卡片 | 状态、法人、规模 |
| 多值标签 | 可点 chips，点击即筛选 | 产业链、荣誉 |
| 层级路径 | 折叠面包屑，默认显示前 N 条 | `人工智能 / 基础层 / 芯片 / CPU` |
| 长文本 | 限高滚动框 + 一键复制 | 经营范围、简介 |
| 多来源列表 | 分组 + 来源与新鲜度标注 | 手机 / 座机 / 邮箱 |
| **时间序列** | **时间线，不是并列 chips** | 高新证书 2013→2025 各年认定与撤销 |
| 明细事实 | 摘要 + 「查看全部」跳转 | 外贸提单（可能上百条） |

高新证书特别说明：同一家公司在 2013–2025 间可能多次认定、中途被撤销。堆成一排 chips 会丢失时间语义，应做**资质时间线**，并标注当前是否有效。

## 22. 列表页 / 地图 / 导出

**列表**——列数不随字段增加而增加，永远只放决策必需的：企业 · 地域 · 行业 · 资本规模 · 触达。新数据类型以**徽章**形式挂在企业名后（如「高新」「产业链」），不新增列。

**筛选维度门槛**——不是入库了就该做筛选项。进入侧栏筛选需同时满足：覆盖率 ≥ 5%、取值可枚举、有明确业务语义。不满足的放进「更多筛选」或只做展示。当前合格的新维度是**产业链**（已上）和**高新**（待上）；`intro`、`registrar` 只展示不筛选。

**地图**——只承载地域与密度，不堆字段；点选后由右侧详情承接。

**导出**——与详情相反，导出是「全字段优先」，用户拿走后自己处理。保持现有宽表 CSV，随入库字段同步扩展。

## 23. 来源与新鲜度

多源合并后这是信任的基础。建议在联系方式每一行标注：

```
手机  138****5678   来源 国家工商底册 · 2023-11   [查看完整]
邮箱  a***@abc.com  来源 产业链基础信息 · 2025-01
```

- 来源名做**人话映射**（`national2023` → 「国家工商底册 2023.11」），不要直接暴露内部标识
- 超过一定年限的号码给出**陈旧提示**
- `[查看完整]` 即架构方案里的 `reveal_contact`，计量 + 审计

主表字段同理，可在区块级标注「部分字段来自产业链基础信息补全」。

## 24. 新数据类型的接入检查表

以后每接一个源，回答完这五个问题再动手：

1. **落在哪张表** —— 主表补空 / 标签 / 旁表 / 独立库？
2. **实测填充率多少** —— 决定进 L1 还是 L4
3. **是否成为筛选维度** —— 过 §22 的三条门槛了吗
4. **什么展示形态** —— 键值 / chips / 时间线 / 明细跳转
5. **来源怎么标** —— `source` 命名与人话映射

# 第五部分 · 质量、风险与验收

## 25. 风险备忘

| 风险 | 应对 |
|------|------|
| 电话空号多 | 保留多来源号码；用 `source` + `collected_at` 判新鲜度 |
| 同码多行字段冲突 | 只补空；冲突保留主库已有值 |
| 产业链主题重叠（机器人 vs 人形机器人） | tags 多值并存，筛选 OR 语义由产品定 |
| 无信用代码行 | 主库导入可用代理键；补全脚本要求合法 18 位码 |
| 02 的「纳税人识别号」非 18 位 | 先校验；失败则名称+省匹配，进待审队列 |
| 01 与旧目录重复跑 | 同码只补空；contacts UNIQUE 去重；断点按文件 |
| 01 全量耗时长 | 单分片约 200s × 853 ≈ 两天，断点挂机 |
| partial 更新误清空列 | 必须 `partial_columns=true`，且只传待更新列 |
| 07 表头极窄（仅邮箱） | 按文件探测表头，宽表/窄表分 parser |
| 09 合规 | 海外个人通讯录慎用，产品默认 B2B 商户字段 |
| 磁盘 | `_unpacked_archives` 与源包重复，稳定后可清 |

## 26. 验收抽检

1. **补全正确性**：某码空字段变非空，原非空字段不变
2. **联系方式**：同号不重复，`has_mobile` 与明细一致
3. **标签**：一家公司可挂多产业链；侧栏筛选条数与详情标签对得上
4. **展示**：无 `intro` 的企业不出现空的「企业简介」区块
5. **来源**：任一手机号都能追溯到 source 与采集时间
